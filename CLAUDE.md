# CLAUDE.md — rules for working on RNNTranslator

These rules apply to every agent and every human who changes this repository. Their purpose is that nothing
drifts: no statement without a check behind it, no number without a source, no artifact that cannot be
rebuilt, no file that quietly stops being true. Where a rule is enforced by a check, the check is named; what the
checks do is in `harness/run.py` and the files it lists under `STATIC` and `ACTIONS`.

## 1. Read before you write

- Before any change, and again after a context compaction, read `README.md` in full, then `CLAUDE.md`, then the
  files the task touches. `README.md` is the current state of the project and its appendix is the list of every
  claim and what pins it; your memory of the tree is not a source.
- After a compaction, also run `uv run python harness/run.py check` before continuing, so the state you work from
  is the tree's, not a summary's.
- `README.md` is rendered from `docs/README.tmpl.md`; never edit `README.md` by hand (`check_readme` would refuse
  the commit). Edit the template and run `uv run python harness/run.py readme`.

## 2. Every claim is pinned or declared a hypothesis

A *claim* is any sentence that asserts something about the system, the data or a result — behaviour, a limit, a
measurement, a reason. A claim is either **pinned** (a test or check that would fail if it were false) or marked
**hypothesis** (believed, not verified). There is no third state; "obvious" is not one.

- In `README.md` this is mechanical: every sentence of the body appears verbatim in the appendix with
  `Pinned by <name>` — a test in `harness/test_claims.py`, an action or a static check in `harness/run.py`, all
  of which the hook runs — or with `Hypothesis`, and a hypothesis also starts with "Hypothesis:" in the body.
  Enforced by `harness/check_readme.py`.
- Every number in `README.md` is a fact placeholder (`{{f:name}}`) resolved by `harness/facts.py` from the
  committed baseline, a constant in the code or a count in the tree. A number that no action produced is not
  written. Enforced by `harness/check_readme.py`.
- In code comments and docstrings the same rule applies by review: a comment a reader could act on without
  reading the code it annotates (a behaviour, a bound, a measurement, a reason) names its pin, for example
  `# pinned by test_rule_parser_bounds`, or starts with `hypothesis:`. A comment that only narrates the lines
  under it is code, not a claim. This part is not yet mechanically checked.
- Documents outside the repository (tracker docs, chat) may be richer, but a number quoted there that is not in
  `harness/baseline.json` must say where it came from and when; the repository never cites them.

## 3. Everything is reproducible and hermetic

- An *experiment* is an action in `harness/run.py`: declared inputs, a sandbox that holds only those inputs, a
  fixed hash seed, a result cached by the hash of inputs + `uv.lock` + interpreter. A result that did not come
  out of an action is an anecdote; to cite it, make it an action and add its number to `harness/facts.py`.
  A new kind of result enters the lattice as items with a chain, not as a number to maximise.
- An *artifact* (the rendered README, the diagram SVG, the baseline, an archive blob) is generated by a script in
  `harness/` from pinned sources, carries a lock with the sha256 of what went in and what came out, and has a
  static check that fails when the two disagree. Never edit a generated file by hand; change its source and
  regenerate.
- Dependencies are pinned by hash in `uv.lock`; the corpus by commit and per-file sha256 in
  `harness/corpus.lock.json`; external tools (PlantUML) by the jar's sha256 in their lock. Adding a dependency,
  a tool or a data file means adding its pin and its schema or check in the same commit.
- Data files have a JSON Schema under `schemas/` and are validated by `harness/check_schemas.py`; the tables also
  satisfy `schemas/tables/integrity.json`. A new data format gets its schema before its first commit.

## 4. The hook is the gate, not an obstacle

- `.githooks/pre-commit` runs the static checks and the actions on the staged tree and compares every item of
  the lattice (`harness/lattice.py`) with `harness/baseline.json` as staged. The order is per item, not per
  aggregate: a corpus sentence is WRONG < REFUSED < RIGHT with UNKNOWN (an unjudged output) below RIGHT and
  incomparable with the rest; the matrix on a sentence is MISFIRE < GAP < AGREE; a negative ACCEPTED < REFUSED; a
  control REFUSED < ACCEPTED. The commit is refused if any item moves down, is removed, or moves to or from
  UNKNOWN — including from one unjudged output to another — without a verdict. Install the hook with
  `uv run python harness/run.py install-hooks`.
- Coverage, BLEU and the other aggregates are views, never gates: refusing a wrong output is an improvement even
  though "coverage" falls.
- When the hook asks for a verdict, judge each unjudged output it shows — the old one, the new one, or both — and
  record it in `harness/adjudications.json` (`right`, `wrong`, or `input_ungrammatical` for a corpus line whose
  English is not standard), with the reason. A verdict is about one output of one sentence and is permanent; judge
  what the output says, never what the gate needs: a new output judged wrong is a down move, and the fix is in the
  code.
- A change that moves items is committed together with its new baseline
  (`uv run python harness/run.py baseline --staged`), and the commit message names what moved and which way.
  `uv run python harness/run.py frontier` shows what remains, grouped by blocker.
- Never weaken a check, a schema, a test or a baseline to make a change pass. If a check is wrong, fix the check
  in its own commit and say in the message what was wrong with it. `git commit --no-verify` is for a broken
  harness only; the commit message says so, and the next commit restores green.
- A check that fails tells you what is incoherent. Fix the cause. If the cause is the README being right and the
  code wrong, fix the code; if the code is right and the README wrong, fix the template and its pin.

## 5. Retirement and scope

- A file that is no longer reachable from the current work leaves the tree in the commit that retires it. What is
  worth reading later goes into `archive/` as a compressed blob with a manifest inside, listed in
  `archive/README.md`; the blob is opaque to text search by design. Git history keeps the rest.
- The matrix parser must never parse a sentence the rule parser refuses, and must agree with it wherever it
  parses; every silent misfire counted by the `matrix` action is a bug in an extracted rule, and the way to
  remove it is to translate that module by hand with complete guards, as `np_module.py` was, verified
  exhaustively — not to tune guards to the corpus.
